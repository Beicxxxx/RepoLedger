# RepoLedger

Follow `AGENTS.md` and the CLI configuration; let the CLI enforce schema, status, relation, anchor, and guard rules.

1. Before referring to an entity, run `repo-ledger lookup "<raw-token>" --json` with the source token unchanged. Exact current IDs and exact registered `legacy` aliases are the only initial candidates. If a raw lookup is unknown, leave it unknown; do not infer casing, separators, zero padding, nearby numbers, or shorthand. If the source is explicitly a code identifier or JSON key, perform that raw lookup first; only if it misses may you try the sole permitted spelling equivalence `TYPE_N` → `TYPE-N`. Do not generate other variants. Resolve a legacy alias to its returned current ID before writing or updating.
   - Every natural-language mention uses the current ID together with its full registered name — every mention, not only the first, and in tables, progress bars, lists, summaries and chat replies too. Copy the name from lookup exactly; never abbreviate it. Write `ID name` (at most one space) or `name（ID）` on the same line, or put ID and name in adjacent table cells. Standalone handoff summaries must repeat the current ID and full registered name; do not rely on a prior bullet or surrounding context. Never reproduce a retired alias in newly written scanned prose, even to explain provenance; leave frozen source unchanged and cite its source path with the current ID and full name instead. Unknown-token diagnostics in chat or CLI arguments may quote the raw token without inventing a name. Bare IDs otherwise belong only in machine-facing positions: code, tests, JSON keys, command arguments in backticks or code blocks, agent-only files.
   - Ordinals carry digits only: section, list and step numbers never contain letters; use dotted levels such as 2.1. A section number is a locator, not a name: refer to a thing by its ID and full name (or a descriptive name if unregistered), and cite a section together with its file name. Old letter labels in historical text stay as written and are decoded, never copied into new text.
   - When `ledger.toml` enables `full_name_guard` / `letter_label_guard`, `repo-ledger check` fails on violations; `repo-ledger check-naming --json` runs only these guards. Historical text is covered by the naming baseline, which may only shrink: fix new text instead of adding rows, and delete a row in the same change that fixes its line.
2. A successful lookup may be cached only within the same session, repository/worktree, branch, handoff context, and unchanged ledger working context. Recheck freshness before reuse: a registry change, including one made by another agent, or a branch/worktree switch or handoff invalidates the cache. If freshness cannot be established, refresh the exact lookup. Do not cache unknown results; refresh their exact lookup before deciding.
3. Before creating an entity, inspect relevant references and run the candidate search: `repo-ledger search "<query>" --json --limit 5`. Search results are candidates, not semantic duplicate proof; run exact lookup on the selected current ID and read its anchor as needed. Allocate only when no existing entity fits and the landing change can carry the row and ID together.
4. Update only an existing current ID, after exact lookup and explicit evidence: `repo-ledger update "<current-ID>" --status "<status>" --note "<evidence>" --expected-status "<old-status>" --json`. Preserve identity, order, relations, and legacy history. `--expected-status` is an optional stale-write check; status transitions are not otherwise enforced. Run `repo-ledger check --json` after any scanned-document write as well as any entity update; it aggregates the legacy guard. Run `repo-ledger check-legacy --json` directly when importing or reviewing frozen text.
5. Allocate genuinely new entities with `repo-ledger allocate <TYPE> "<title>" --anchor <tracked-file>`. Use the returned ID; never predict one. A `--legacy` value records only a documented pre-existing alias and is never a new spelling to write. Drafts, task briefs, and reviews do not mint IDs. Mint only in the designated main workspace; the short lock protects one local allocation, not cross-clone uniqueness.
6. On failure, inspect the reported location. Do not fabricate registration, use a shape regex for retired codes, or widen ignores/exemptions to make checks pass. Read one entity and its anchor as needed rather than preloading the registry. `check` is working-tree validation only; staged, commit-tree, incremental, and historical-anchor views remain unsupported.
7. Per-type index pages are generated, never hand-edited: `repo-ledger index` writes `README.md` plus one `<TYPE>.md` per declared type into `--out DIR` or the `[index] out_dir` of `ledger.toml`, and `repo-ledger index --check --json` compares them byte for byte without writing. When the project declares `[index]`, regenerate the pages in the same change as any registry edit (allocate or update) and commit them together. With `[index] check = true`, `repo-ledger check` reports missing, stale or unexpected pages as `ERR_INDEX_STALE`; fix missing or stale pages by regenerating, never by editing a page. index never deletes: an unexpected page is either left over from a removed type or a file that belongs elsewhere, so delete or move it deliberately. The pages are for human browsing; use `lookup` for entity data.

cross-harness-sync is optional and independently installed. RepoLedger does not manage git pull/push, handoff documents, approval roles or session-wide writer policies.
